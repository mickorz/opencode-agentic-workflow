# 从「提示词自动生成」到「注册式流程」——v1 → v2 的核心架构转变解析

**日期**：2026-10-08 ｜ **性质**：设计动机解析（回答高频问题：「v1 直接输提示词就
自动生成 workflow JS，为什么 v2 测试要建 flow.json？」）

## TL;DR

v2 并没有丢掉「说句话就生成流程」的能力——它以 **workflow-authoring skill +
`workflow_define` 工具**的形态重建了这条链路（校验 → 注册 → 落盘，全程零手工
编辑文件）。变掉的是**底层契约**：流程从「每次对话现场生成的临时 JS 脚本」变成
「带 `id@version` 身份的注册资产」。这个身份是 v2 全部 durable 能力（断点续跑、
版本一致性、前缀跳过、metrics、面板详情/会话回放）的地基——**没有稳定身份的
流程是不可恢复的**。测试时手写 `flow.json` 只是因为验收要一个**确定性夹具**，
不是 v2 的日常用法。

## 一、v1 是怎么工作的

```text
用户提示词（自然语言）
  → 主 agent 按内置 skill 现场生成一段 JS orchestration script
  → Runtime 直接加载这段 JS，调度独立子会话执行
```

- **零前置**：不用预先定义任何东西，对话里描述需求即可
- **代价**：生成的脚本是**临时产物**——没有稳定标识、没有版本、跑完即弃。
  同样的提示词再问一次，生成的脚本可能就不一样了
- v1 的「journal 回放」按**调用位置**工作，绕开了对流程身份的依赖——但这也
  意味着跨会话恢复、多版本共存、精确重附着这些能力无从谈起

## 二、v2 是怎么工作的

```text
流程 = 注册资产（id@version）
  ├─ 内置流程：smoke / reliable / artifact / feature-development（装完即用）
  ├─ 声明式 JSON：flows 目录装载（P4），或对话中 workflow_define 生成（P0-2）
  └─ 代码式 TS/JS：编译产物注册（dist/workflows）
      ↓
workflow 工具只跑「已注册」的流程（flow=<id>，缺省 smoke）
```

`workflow` 工具**不接受**「现场生成一段逻辑直接跑」。为什么这么设计：

| v2 能力 | 为什么依赖「注册身份」 |
|---|---|
| 断点续跑（resume） | journal 记录 `workflow {id, version}`；恢复时 registry.resolve **精确版本重附着**——挂掉的 run 必须对得上当初的定义 |
| 已完成步骤前缀跳过 | 要判断「第 N 步的输出属于当前这个流程定义」，前提是定义身份不变 |
| 版本契约 | 同 id 多版本共存、升版本走显式 bump；临时生成物没有「版本」可言 |
| metrics / 成本核算 | 按流程聚合统计，键就是 id |
| 面板详情 / Open Session 回放 | journal 步骤 → 会话 ID → 完整对话，全靠 run 与定义的稳定关联 |

一句话：**v1 生成的是「代码」，v2 注册的是「资产」；资产才有身份，身份才可恢复。**

## 三、「提示词生成」链路在 v2 的形态（没有消失）

v1 的零代码体验以声明式形态重建，两层组成：

1. **`workflow-authoring` skill**（安装器默认拷入）：教主 agent 走
   「对话澄清 → 构造 JSON → `workflow_define` 落盘注册 → `workflow` 试跑」
2. **`workflow_define` 工具**（P0-2）：主 agent 对话中直接定义流程——
   校验（与装载器同一套规则，错误逐一指名）→ 注册（同 id@version 拦截、
   内容相同幂等、内容不同要求升版本）→ 落盘到 flows 目录

**实际体验**：配置里有一行 `"workflows": ["flows"]`，然后直接对 agent 说——

> 帮我定义一个流程：先调研 X，再并行从 A/B 两个角度各写一段，最后汇总。

agent 会调 `workflow_define` 完成 JSON 构造、注册、落盘，接着就能跑。
**全程不碰编辑器**——和 v1 的体感一致，产物却从临时脚本变成了可版本化、
可恢复、可复用的注册资产。

（未配置 workflows 目录时 define 会精确报错并给出补配方法，不会静默降级。）

## 四、那为什么手动验收文档让你手写 flow.json？

三个具体原因，都不是「v2 必须手写」：

1. **测的是运行时，不是生成质量**：面板验收（P 系列）要一个**确定性夹具**——
   步骤数、步骤名、pipeline 条目数全部钉死，断言和肉眼比对才稳定。让 agent
   现场生成会引入无关变量（生成本身的波动）。
2. **夹具形态有针对性**：`hello.json` 的 pipeline 步（2 条目）是专为 P-5
   「会话回放区」设计的——需要一步多会话的形态来验证 P2-13 的多会话聚合。
3. **更省事的路当时没写进环境准备**（现已补充）：其实零准备也能测——
   内置 `flow=smoke` 开箱即跑；或者对话里让 agent 用 workflow-authoring
   定义。手写 JSON 只在要精确控制夹具形态时才需要。

## 五、速查对照

| 维度 | v1（opencode-dynamic-workflows） | v2（opencode-agentic-workflow） |
|---|---|---|
| 提示词生成 | ✅ 内置（生成临时 JS） | ✅ skill + `workflow_define`（生成注册 JSON） |
| 零代码体验 | ✅ | ✅（配置一行 workflows 目录后） |
| 流程身份 | ❌ 无（临时脚本） | ✅ id@version 注册资产 |
| 跨会话 resume | ❌ | ✅（journal + 精确版本重附着） |
| 多版本共存 | ❌ | ✅（registry 同 id 多版本，取最新） |
| 声明式定义 | ❌（只能 JS） | ✅ JSON（agent 友好，diff 友好） |
| 开箱即用流程 | 少量 | smoke / reliable / artifact / feature-development |
