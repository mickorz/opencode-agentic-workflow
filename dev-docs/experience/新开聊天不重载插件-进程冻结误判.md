# 新开聊天不重载插件：skill 重读掩盖插件进程冻结

**日期**：2026-10-09（v0.6.4 当日）　**版本**：0.6.3 用户实测 / 0.6.4 修复自诊断

## 问题现象

用户在 testworkflow 项目用自然语言创建 `wordfreq-mnemonic` 流程（0.6.3
skill 已生效——主 agent 行为完全符合新纪律：快速动笔、不探索安装位置、
文件一次写对）。但调用 workflow 工具时：

1. `workflow not found: wordfreq-mnemonic`，重试无效
2. available 列表里只有 `calc`——**会话开始前就在磁盘上的
   keyword-report、pinyin-mnemonic 都不在**
3. 宿主日志零装载错误

用户观感：「升级了反而坏了」。

## 排查过程

1. 宿主日志（`~/.local/share/opencode/log/opencode.log`）：无任何 flows
   装载错误（排除「文件坏了」）
2. 用缓存里的 0.6.3 loader 对同一 flows 目录装载：**四个流程全注册、
   零错误**（排除 loader bug；session agent 写的 wordfreq-mnemonic.mjs
   本身也一次写对）
3. 审读 `refreshCustomWorkflows`：增量语义正确（同 id@version 跳过、
   文件级错误不阻断、注册失败单独收集）
4. 缓存考古：唯一目录 0.6.3@11:43:54；行为特征三连定性——
   - 列表冻结在 calc = 进程启动时磁盘上只有 calc（10:10-10:29 之间）
   - 无重扫 = 插件 <0.6.1
   - 无装载错误 = 不是装载失败，是**根本没装载**
   → 服务该会话的插件实例是 **10:16 时代的 0.6.0 长命进程**，
   后续所有「重启」（新开聊天）都没换过血

## 根因

**插件随 opencode 进程加载一次就冻结；新开聊天会重读 skill 却不重载
插件。** 两者的更新节奏错位，造成验证信号错位：skill 改善让会话
「看起来升级成功了」，插件运行时其实还是 0.6.0——重扫（0.6.1+）自然
不存在，available 列表自然停在进程启动瞬间的磁盘快照。

## 解决方案

1. **用户侧**：完全退出 opencode（进程退出，不是新开聊天）再启动
2. **产品侧（v0.6.4）**：`formatUnknownFlowMessage`（custom-flows.ts）
   把三段信息钉进 not found 报错：
   - available 清单（live registry）
   - flows 装载错误前 3 条（原有的作者自诊断）
   - **`plugin v<版本>` + 「plugins load once per opencode process…
     a new chat does not reload plugins」**——进程冻结从沉默状态变成
     报错里一眼可读的显式信号

## 预防/注意事项

- **2026-10-10 复发（升级版陷阱）**：0.8.3/0.8.4/0.8.5 连发三版全部
  「无效」，用户反复重启仍是 0.8.2 行为。考古：缓存目录唯一世代
  10-09 20:49（0.8.2），且存活进程含 `opencode serve --service`
  （后台服务）与**两个周日启动的长命 TUI 客户端**——「退出 TUI」
  杀不掉服务进程与其他终端的客户端。教训：多终端 + 常驻服务的
  场景，「完全退出」必须 `pkill -f opencode` 级别；另清
  `~/.cache/opencode/npm/@mickorz` 强制重新解析 @latest，避免
  缓存世代不刷新。
- 诊断口诀：**日志无装载错误 + available 缺老文件 = 插件进程冻结**，
  别去怀疑 flows 文件
- 排查这类问题的证据顺序：①报错里的 `plugin v…` vs 安装版本
  ②宿主日志 ③用缓存 loader 对真实 flows 目录做装载复现（发布产物
  验证模式）④缓存目录时间戳考古
- E2E 盲区提醒：dist 级验证证明的是「代码能」，证明不了「宿主进程
  在跑这份代码」——进程寿命是独立维度，只能靠版本自暴露（本坑的
  直接教训）
